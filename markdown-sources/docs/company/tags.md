# Cloud Resource Tagging / Labelling Standard

AWS and Azure call them **tags**; GCP calls them **labels**. This standard defines the tags and labels for resources created in AWS, Azure and GCP.

Tags should be applied to all application resources that allow tagging. This includes server and serverless compute, storage, security groups, load balancers, certificates and more.

Some tags are required to meet Sysco standards. Resources missing required (mandatory) tags may be prevented from launching or functioning.

## Mandatory tags (AWS, Azure and GCP)

There are 5 mandatory tags. Every AWS and Azure resource must have these tags, and every GCP resource must have the matching labels:

1. `Technical:ApplicationID` (GCP label: `technical_applicationid`)
2. `Technical:ApplicationName` (GCP label: `technical_applicationname`)
3. `Technical:Environment` (GCP label: `technical_environment`)
4. `Technical:PlatformOwner` (GCP label: `technical_platformowner`)
5. `Technical:PatchWindow` (GCP label: `technical_patchwindow`)

| AWS and Azure tag | GCP label | Sample value (AWS and Azure) | Sample value (GCP) | Required |
| --- | --- | --- | --- | --- |
| Technical:ApplicationID | technical_applicationid | APP-002417 | app-002417 | Mandatory |
| Technical:ApplicationName | technical_applicationname | RME | rme | Mandatory |
| Technical:Environment | technical_environment | NONPROD | nonprod | Mandatory |
| Technical:PlatformOwner | technical_platformowner | ADLM@sysco.com | adlm_sysco-com | Mandatory |
| Technical:PatchWindow | technical_patchwindow | amr_s_tue_2230_np_win_r | amr_s_tue_2230_np_win_r | Mandatory |

### Technical:ApplicationID (mandatory)

GCP label: `technical_applicationid`. Example: `APP-002417` (AWS and Azure), `app-002417` (GCP).

The official Application ID, generated by Sysco's CMDB. If you are unsure of your Application ID or need a new one, contact Enterprise Architecture: [EA Confluence space](https://syscobt.atlassian.net/wiki/spaces/EA).

### Technical:ApplicationName (mandatory)

GCP label: `technical_applicationname`. Example: `RME` (AWS and Azure), `rme` (GCP).

The common, user-friendly name mapped to the Application ID in the CMDB: [CMDB business application list](https://sysco.service-now.com/nav_to.do?uri=%2Fcmdb_ci_business_app_list.do%3Fsysparm_query%3D%26sysparm_first_row%3D1%26sysparm_view%3Dbusiness_application_readonly).

GCP value rules:

- Replace spaces with an underscore ( _ ).
- Dashes ( - ) stay as they are.
- No repeated symbols such as `__` or `--`.
- Example: `GCP - Google Cloud Platform` becomes `gcp_-_google_cloud_platform`.

### Technical:Environment (mandatory)

GCP label: `technical_environment`. Example: `NONPROD` (AWS and Azure), `nonprod` (GCP).

The name of the logical build environment for the service. Valid values: DEV, QA, PROD, NONPROD, SBX (Sandbox) and STG (Staging).

### Technical:PlatformOwner (mandatory)

GCP label: `technical_platformowner`. Example: `ADLM@sysco.com` (AWS and Azure), `adlm_sysco-com` (GCP).

An email address, usually the Product or Platform Owner. A team distribution list for the technical product or platform team is also accepted, but only ONE email address is allowed.

### Technical:PatchWindow (mandatory)

GCP label: `technical_patchwindow`. Example: `amr_s_tue_2230_np_win_r` (same format for AWS, Azure and GCP).

This tag is required whether you patch your workloads through CI/CD or rely on Enterprise Patching.

- There are 21 standard patch windows. All valid values are in the [patch window list](https://sysco.sharepoint.com/:x:/s/HybridCSportal/ERzbIOigaThNl30i8YXE8EwBHphJvaH6ZgKZt3v3Bxzgbg?e=bsUIfA).
- The value `HCO-offboard` is not allowed: it excludes servers from patching. An SCP-level restriction blocks it in all user accounts. To use it, get approval from the VTM team.
- Change this tag at least one week before monthly patching starts.

## Automation tags

Automation tags manage automated services for application resources. Teams maintain the values. They are optional today; some will become required later, and teams will be told how to use them when the automation is in place.

| AWS and Azure tag | GCP label | Description | Sample value | Required |
| --- | --- | --- | --- | --- |
| Automation:SnapshotMgmt | automation_snapshot_mgmt | Lets team-managed resources use the shared snapshot service | Enabled / Disabled | No |
| Automation:RightSizing | automation_right_sizing | Not yet available; will let team-managed resources use the shared right-sizing service | Enabled / Disabled | No |
| Automation:{ServiceName} | automation_{service_name} | Supports specific requirements of a service | Automation:CloudCustodian:TerminationDate | No |

### Automation:PMC (optional)

GCP label: `automation_pmc`. Non-prod only.

Assigns the matching ParkMyCloud schedule to the workload automatically. You still need to create logical groups and delays in the PMC group so workloads start and stop in order. Valid values are on the [ParkMyCloud page](https://syscobt.atlassian.net/wiki/spaces/SyscoGo/pages/458851215/ParkMyCloud). For a new policy or schedule, contact Hybrid Cloud Services (HybridCloudServices@sysco.com).

### Automation:Backup (optional)

GCP label: `automation_backup`. Controls the backup of VMs across cloud providers.

- Values: `disable`, `clops-default` (the default for production) or `clops-custom-<number of days>`.
- If a stand-alone production EC2 instance has no `Automation:Backup` tag, it is tagged with the default value and backed up with the Sysco default backup policy, which adds cost.
- If the value is `disable`, no backup policy is attached.
- For a custom snapshot retention period, contact Cloud Operations (cloudoperations@sysco.com); the value then becomes `clops-custom-<number of days>`.

## Tag limits (all clouds)

- Maximum number of tags per resource: 50.
- Each tag key must be unique on a resource, and each key can have only one value.
- Maximum key length: 128 Unicode characters (UTF-8).
- Maximum value length: 256 Unicode characters (UTF-8).
- Allowed characters across services: letters, numbers, spaces and `+ - = . _ : / @`. EC2 allows any character, but other services are stricter.
- Tag keys and values are case-sensitive.
- Don't use the `aws:` prefix in keys or values; it is reserved for AWS. Tags with this prefix can't be edited or deleted and don't count toward the 50-tag limit.

## GCP label rules

GCP is much more restrictive with labels than AWS and Azure are with tags.

- Keys and values can be at most 63 characters each.
- Keys and values can contain only lowercase letters, numbers, underscores and dashes. International characters are allowed.
- Label keys must start with a lowercase letter and cannot be empty.
- Labels can be added to projects and resources, but not to folders.
- Not all resources support labels: see the [list of supported services](https://cloud.google.com/resource-manager/docs/creating-managing-labels#label_support).
- Resources listed as Alpha are not supported in gcloud or the console yet; use the Alpha API to label them.
- Google strongly recommends not storing sensitive data in labels, such as a person's name, title or email address.

## Azure resource group tag inheritance

- Required tags set at the Resource Group level are inherited automatically by new Azure resources.
- Existing resources get the updated values the next time they are modified.
- Changes made directly to an inherited tag on a resource may be reverted to match the Resource Group.
- Where possible, update tags at the Resource Group level to keep them consistent.
